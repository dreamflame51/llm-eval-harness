# llm-eval-harness

Небольшой RAG-пайплайн поверх пяти публикаций NIST и стенд, который меряет,
работает ли он на самом деле.

Смысл проекта — в измерении. Добиться выдачи, которая «выглядит релевантно»,
легко; стенд проверяет, действительно ли найденный текст **подтверждает** ответ
и отказывается ли модель, когда в корпусе ответа нет.

**[Сводная страница](https://claude.ai/artifact/5DtQB21Gu6ZwAvzj5YbMxj)** — все числа
отсюда, нарисованные: три ретривера, судья против ручной разметки построчно, RAGAS
против DeepEval, матрица трассируемости и недостающие уровни V-модели. Собирается
скриптом `scripts/make_dashboard.py` из закоммиченных файлов, модель для отрисовки не
вызывается.

English: [../README.md](../README.md) ·
Журнал проблем: [lessons.ru.md](lessons.ru.md) ·
Что утверждается и чем проверяется: [traceability.md](traceability.md) ·

## Как устроено

```
PDF ──load_pdf──> текст ──chunk_text──> чанки ──> Chroma ──search──> топ k ──> LLM ──> ответ
```

| модуль | что делает |
|---|---|
| `loader.py` | PDF в текст (pypdf) |
| `chunker.py` | текст в чанки, окно 800 / нахлёст 160 |
| `store.py` | индекс Chroma, эмбеддинги `all-MiniLM-L6-v2` |
| `ingest.py` | собирает индекс из `data/corpus/*.pdf` |
| `pipeline.py` | вопрос в ответ, через Ollama |
| `dataset.py` | загружает `eval/ground_truth.yaml` |
| `validate.py` | проверяет, что фикстура ещё соответствует корпусу |
| `evaluator.py` | метрики ретривала |
| `refusal.py` | проверка отказов |

## Установка

Нужны Python 3.14, [uv](https://docs.astral.sh/uv/) и Ollama с `gemma4`
(только для генерации ответов; метрики ниже работают без неё).

```bash
uv sync
```

Пять исходных PDF лежат в `data/corpus/`. Собрать индекс:

```bash
uv run python -m llm_eval_harness.ingest    # ~5000 чанков, несколько минут
```

Они закоммичены намеренно: эталонный набор цитирует точные спаны именно этих
файлов, так что другая копия — или другое извлечение — сделает его невалидным.
Публикации NIST в общественном достоянии.

Индекс не коммитится. После смены модели эмбеддингов или размера чанка
пересобирать с нуля (`rm -rf data/chroma`): старые векторы несовместимы, а
`upsert` их не удалит.

## CI

[![CI](https://github.com/dreamflame51/llm-eval-harness/actions/workflows/ci.yml/badge.svg)](https://github.com/dreamflame51/llm-eval-harness/actions/workflows/ci.yml)

У раннера GitHub Actions нет ни GPU, ни Ollama — и это то ограничение, под которое
стенд спроектирован, а не то, которое он обходит. Вердикты судьи и оба файла с
оценками библиотек закоммичены ровно затем, чтобы машина без модели могла пересчитать
и напечатать каждое число из этого README.

Поэтому джобы разделены по тому, **что каждому нужно**, а не по тому, что они такое
([`.github/workflows/ci.yml`](../.github/workflows/ci.yml)):

| джоб | нужно | когда |
|---|---|---|
| `lint` | ничего | каждый push |
| `tests` | PDF корпуса и модель эмбеддингов, кэшируется после первого раза | каждый push |
| `metrics` | только закоммиченные файлы — ни модели, ни индекса | каждый push |
| `retrieval` | индекс Chroma, пересобирается из PDF | вручную, падение допустимо |

`metrics` гоняет `validate`, судейскую метрику отказа, отчёт по судьям и сравнение
библиотек, складывает вывод в артефакты и пишет сводку прогона: ссылку на страницу
выше и **числа именно этого прогона под ней**. Ссылка постоянная, а страница
перевыкладывается руками — соседние числа и есть то, что не даёт ссылке указывать на
цифры, которых никто не пересчитывал.

Ничто в `metrics` не является гейтом. Приёмочных порогов в проекте нет ни у одной
метрики (см. [v-model.md](v-model.md)), а порог, придуманный ради зелёного пайплайна,
превращает измерение в ритуал. Гейтом являются: сюита, линт и
`tests/eval/test_regression.py`, который прибивает каждое отчётное число равенством.
Сдвинулось — сборка красная, и это надо объяснить в коммите.

`retrieval` вручную, потому что пересборка индекса — это ~5000 чанков эмбеддингов, и
`continue-on-error`, потому что сдвиг метрики на 0.02 — измерение, а не повод красить
пайплайн.

## Команды

Воспользоваться самой системой:

| команда | что делает |
|---|---|
| `uv run python scripts/ask.py "ваш вопрос"` | отвечает по корпусу и показывает фрагменты, из которых взял ответ |
| `uv run python scripts/serve.py` | то же самое в браузере, на 127.0.0.1 |

Фрагменты показываются потому, что худший отказ системы — правдоподобная выдуманная
цифра: видя текст-источник, ответ проверяешь взглядом, а не открывая PDF. Он же
отличает правильный отказ от промаха ретривала. Обе команды работают целиком на этой
машине — опубликованная страница до локальной модели не достучится, поэтому эта
раздаётся, а не выкладывается ссылкой.

| команда | на какой вопрос отвечает |
|---|---|
| `uv run python -m llm_eval_harness.validate` | эталонный набор ещё валиден? |
| `uv run python -m llm_eval_harness.evaluator` | находит ли ретривал подтверждающий текст? |
| `uv run python -m llm_eval_harness.refusal` | отказалась **и** ничего не выдумала? (из кэша, без модели) |
| `uv run python scripts/judge_report.py` | оба судьи, ручная разметка и где они расходятся |
| `uv run python scripts/smoke.py` | быстрая проверка глазами на трёх вопросах |
| `uv run python scripts/calibrate.py` | пересчитать порог дистанции |
| `uv run python scripts/stability.py` | воспроизводима ли оценка отказов? |
| `uv run python scripts/sweep.py` | какой размер чанка ищет лучше? (минуты) |
| `uv run pytest` | тесты стенда |
| `uv run pytest practice` | учебные задачи, вынесены из основного прогона |

Перезапускать только когда меняется само судейство — каждой нужна Ollama и
примерно 15 минут на этом железе:

| команда | на какой вопрос отвечает |
|---|---|
| `uv run python scripts/judge_refusals.py --model qwen3:8b` | отсудить зафиксированные ответы, наполнить кэш |
| `uv run python scripts/calibrate_judge.py --model qwen3:8b` | способен ли судья выдать вердикты, которые обязан? |
| `uv run python scripts/label_refusals.py` | разметить зафиксированные ответы руками |
| `uv run python scripts/record_answers.py` | перезаписать ответы (разметка при этом теряется) |
| `uv run python scripts/live_check.py` | ведёт ли живой пайплайн себя так, как описывают прибитые числа? (~20 мин) |
| `uv run python scripts/usefulness.py` | посидеть с системой на реальных задачах и записать, была ли от неё польза |

**Свежие ответы генерируют три команды, и они не взаимозаменяемы.** Они начали
сходиться друг к другу случайно, поэтому карта записана здесь, а общая сверка с
пином вынесена в `llm_eval_harness/pins.py`:

| команда | на что отвечает | валит релиз? |
|---|---|---|
| `refusal.py --live` | что система говорит прямо сейчас? Сверка по фразам, ответы печатаются целиком | нет — это диагностика |
| `stability.py` | насколько число гуляет, когда ничего не менялось? N прогонов, каждый в свежем процессе | да, если вопрос разошёлся с пином |
| `live_check.py` | ведёт ли живая система себя так, как говорит замороженный набор? Один прогон, судья по обеим осям | да |

## Эталонный набор

`eval/ground_truth.yaml` — 38 записей:

- **26 отвечаемых**: вопрос, эталонный ответ и точные спаны, которые его
  подтверждают.
- **12 на отказ**: корпус ответить не может, единственный правильный ответ —
  отказ. Два класса по шесть, считаются раздельно: `in_corpus_gap` (документ
  есть, факта нет) и `out_of_corpus` (документа нет вовсе). Пробелы покрывают
  все документы, а четыре отсутствующих документа из шести — те, на которые
  корпус *ссылается*: FIPS 199, SP 800-39, SP 800-73, FIPS 201-3. Модель видит
  ссылку и не должна отвечать так, будто документ у неё есть.

У каждой записи на отказ записан поиск, которым установлено отсутствие, и второй
флаг `topic_in_corpus`: присутствует ли *тема* вопроса где-нибудь в корпусе,
независимо от документа. Он не участвует в оценке. Он есть потому, что
`refusal_type` плохо предсказывает сложность — единственный воспроизводимый
провал это запись класса `out_of_corpus`, тему которой корпус разбирает
подробно, — а перекраивать классы позже не должно означать перепроверку
двенадцати записей. Измерено, а не предположено: **10 записей из 12 топически
присутствуют**, и это то, что корпус из пяти документов на одну тему делает с
набором на отказ. Высокую долю отказов читать с этой поправкой: лёгкий конец
набора здесь почти пуст.

Эталонные цитаты цитируют вывод `load_pdf()`, а не PDF таким, каким он выглядит
на экране. Артефакты извлечения сохранены дословно (`T he`, `process43`,
`Rivest-Shamir- Adleman`). Убирать их нельзя: ретривер индексирует именно
покорёженный текст, и «чистая» цитата засчитала бы корректный ретривал как
промах.

**Наборов записанных ответов на отказ два, и сравнение между ними — само по
себе результат.** Записанный ответ это фотография системы, которая его выдала,
поэтому, когда в ретривал вплавили BM25, двенадцать ручных меток перестали
описывать работающую систему. Набор записан заново и размечен заново — **рядом**
со старым, а не поверх: метка описывает один ответ против тех чанков, из
которых он написан, и смену не пережила ни одна (`--keep-labels` перенёс ровно 0).

| набор | ретривер | записан | судья | фразы | руками |
|---|---|---|---|---|---|
| `eval/dense_baseline/refusal_answers.yaml` | плотный | 14.09 | 10/12 | 11/12 | 11/12 |
| `eval/dense_baseline/refusal_answers.control.yaml` | плотный | 16.09 | 10/12 | 11/12 | 11/12 |
| `eval/refusal_answers.yaml` (текущий) | гибрид | 16.09 | 10/12 | 11/12 | **9/12** |

Средняя строка — контроль, и она здесь потому, что сравнение двух **записей** это
не сравнение двух **систем**: генератор переписывает между процессами большую
часть ответов, поэтому в разнице между 14.09 и 16.09 лежит и день тоже.
Зафиксировать день и сменить только ретривер — вот что даёт средняя строка.

**Вплавленный BM25 стоил двух записей заземления.** Обе плотные записи по
разметке дают 11/12 независимо от дня; гибридная, сделанная в тот же вечер, —
9/12. Все автоматические приборы этого не видят: судья трижды говорит 10/12,
список фраз трижды 11/12, потому что оба сдвига лежат на оси `fabricated`, где
судья согласуется с человеком на уровне случайности (ниже).

Механизм прослежен, а не угадан. На вопрос, какие биометрические форматы задаёт
SP 800-76 — документа в корпусе нет, — плотная запись отказывается, гибридная
утверждает про CBEFF, взяв это из чанка SP 800-78-5, который стоит четвёртым в
гибридной пятёрке и в плотной не встречается вовсе. И это не BM25-only чанк:
фузия подняла чанк, который плотный поиск держал ниже отсечки. Метрики ретривала
меряют, приходит ли нужный текст, а не что приходит рядом с ним
([#25](lessons.ru.md#25), [#27](lessons.ru.md#27)).

## Что показывают метрики

**`validate`** — целостность фикстуры. Два разных отказа, разделены:

| результат | что значит | что чинить |
|---|---|---|
| `MISSING` | цитаты нет в корпусе нигде | фикстуру |
| `SPLIT` | есть, но ни один чанк не держит её целиком | размер чанка / нахлёст |

Сейчас: 48 цитат из 51 чистые, 0 missing, 3 split.

**`evaluator`** — ретривал. Четыре числа по одному и тому же топ-5, потому что у
вопроса «отдал ли ретривер свидетельство?» не один честный ответ.

| метрика | как читать | сейчас |
|---|---|---|
| `hit@5` | один чанк держал эталонную цитату целиком | **0.538** |
| `covered@5` | пять чанков держали её *вместе* | **0.577** |
| `coverage@5` | средняя доля цитаты, которую держали пять чанков | **0.606** |
| `MRR` | среднее от 1/позиция; промах считается за 0 | **0.362** |

Это оценка того ретривера, которым отвечает `pipeline.py`, — плотный плюс BM25.
До 16.09 здесь стояли числа чисто плотного поиска, хотя продукт уже сутки им не
пользовался ([#25](lessons.ru.md#25)). Отдельная колонка для плотного никуда не
делась: её печатает `scripts/compare_retrievers.py`, где сравнение ретриверов и
есть вопрос.

`hit@k` игнорирует позицию, `MRR` — нет: система, которая всегда ставит нужный
чанк пятым, для первой метрики идеальна, для второй плоха.

Ещё `hit@k` выставляет ретриверу счёт за нарезку. Цитату, разрезанную границей
чанка, невозможно засчитать при сколь угодно хорошем поиске, так что метрика
меряет заодно и то, насколько цитатам повезло с границами. `covered@k`
принимает цитату, собранную из нескольких найденных чанков: это стоит второго
слота из k — цену, которую конфигурация действительно платит, — вместо глухой
стены. Разница между ними, здесь одна запись, и есть цена нарезки.

В покрытие идут только непрерывные серии от пяти слов. Свободно разбросанные
слова дали бы покрытие на любом английском тексте.

**Потолки у двух метрик разные, и сравнение обязано это учитывать.** У `hit@5`
он 24 из 26: у двух записей единственная цитата, которую ни один чанк не держит
целиком. У `covered@5` он 26 из 26, потому что k подряд идущих чанков
восстанавливают `(k-1) * stride + size` = 3360 символов непрерывного текста при
800/160, а самая длинная эталонная цитата — 414. Поэтому перебор ниже сравнивает
`covered@5`, а не `hit@5`.

Отчёт разделяет провалы по тому, что на самом деле пошло не так: цитата найдена,
но размазана по нескольким чанкам; найдена частично; не найдена вовсе. Это три
разных дефекта, которые `hit@k` показывал одним числом.

**`refusal`** — заземлённость. Неотвечаемый вопрос пройден только тогда, когда
модель **отказалась и ничего не выдумала**. Это два разных вопроса, и решаются
они по отдельности LLM-судьёй: `refused` — по одному лишь ответу, `fabricated` —
против тех пяти чанков, которые генератор реально видел.

| | отказалась, ничего не выдумала |
|---|---|
| ручная разметка | **9/12** |
| судья, `qwen3:8b` | 10/12 |
| список фраз (tripwire) | 11/12 |

по классам, по разметке: `in_corpus_gap` 5/6, `out_of_corpus` 4/6.

**Эти числа не двигаются между прогонами.** Двенадцать ответов заморожены в
`eval/refusal_answers.yaml`, размечены руками, вердикты судьи закоммичены в
`eval/judge_cache/`, поэтому `refusal` читает их, не загружая модель. Прежние
числа отказов в этом README были выборками дрейфующего генератора; эти — нет.

**По одной оси судья решён, по второй — на уровне угадывания.** Против ручной
разметки, переделанной 16.09 на наборе, где выдумки действительно есть:

| ось | `qwen3:8b` | `gemma4` |
|---|---|---|
| `refused` | 12/12, каппа **1.00** | 11/12, каппа 0.75 |
| `fabricated` | 9/12, каппа **-0.12** | 10/12, каппа 0.00 |

Сырое согласие 75-83% во второй строке это и прячет: выдумок в разметке две из
двенадцати, поэтому судья, всегда говорящий «нет», набирает 10/12. Человек нашёл
две, `qwen3` — одну, и другую, `gemma4` — ни одной.

**Одна из этих двух — ровно тот случай, ради которого судья и строился.** Ответ
отказывается, а следом называет частоту, которой в его чанках нет: список фраз
пропускает его по построению, `qwen3` пропускает тоже. Эта клетка пустовала всю
жизнь фикстуры — потому утверждение и нельзя было проверить; теперь она занята,
и не поймал никто. n равно двенадцати, каппы хрупкие; направление — нет.
См. [#20](lessons.ru.md#20) и [#28](lessons.ru.md#28).

Список фраз оставлен рядом: он решает только отказ, поэтому hedge, который
отказался и подставил цифру, для него безусловный успех. Каждое расхождение
между ними печатается. См. [#18](lessons.ru.md#18).

Свои же ответы судила `gemma4` — ради этого второй судья и запускался.
Self-preference, за которым ставили контроль, не обнаружился; обнаружилось
обратное, систематически, на четырёх записях одной формы — [#19](lessons.ru.md#19).

`scripts/calibrate_judge.py` существует потому, что судья, отвечающий «ничего не
выдумано» на всё, набирает 92% против набора с одной выдумкой. Четыре
синтетических ответа с заранее зафиксированными вердиктами; обе модели проходят,
значит чистый вердикт — это вердикт, а не залипшая ось — [#20](lessons.ru.md#20).

`pipeline.py` декодирует жадно с фиксированным seed, и это убрало разброс между
повторами **внутри одного процесса** — проверить можно
`uv run python scripts/stability.py`, но ничего другого эта проверка увидеть и
не может: она повторяет прогоны в цикле, а не в новом процессе. Между процессами
модель по-прежнему плывёт: тот же вопрос, те же пять найденных чанков, те же
дистанции до четвёртого знака — другой ответ. Вероятная причина — раскладка слоёв
между GPU и CPU, которая заново решается при каждой загрузке модели (4 ГБ VRAM
модель целиком не держат), а жадное декодирование дальше расходится с первого же
перевернувшегося argmax. Фиксированный seed тут не помогает: сэмплирования нет.

То есть число со стороны генерации воспроизводимо внутри сессии и не
воспроизводимо между сессиями. См. [lessons.ru.md](lessons.ru.md) #17.

## Конфигурация выбрана измерением, а не на глаз

`800/160` и `all-MiniLM-L6-v2` получены перебором, где за раз двигался один
фактор, а текущая конфигурация была контролем:

Воспроизвести — `uv run python scripts/sweep.py`. Колонка `потолок` это предел
каждой метрики на этом наборе: лучшее, что она в принципе может вернуть, что бы
ретривер ни делал. Все строки здесь считаны **плотным** поиском, и так и надо:
сравнивается размер чанка, значит ретривер обязан стоять на месте. Поэтому в
строке 800/160 стоит 0.423, а в таблице выше та же конфигурация с вплавленным
BM25 даёт 0.538.

| size / overlap | чанков | потолок hit / cov | hit@5 | cov@5 | coverage@5 | MRR |
|---|---|---|---|---|---|---|
| 1000 / 200 | 4044 | 25 / 26 | 0.308 | 0.308 | 0.383 | 0.218 |
| **800 / 160** | **5054** | **24 / 26** | **0.423** | **0.462** | **0.544** | **0.277** |
| 500 / 100 | 8085 | 23 / 26 | 0.308 | 0.308 | 0.423 | 0.167 |
| 300 / 60 | 13474 | 12 / 26 | 0.038 | 0.154 | 0.333 | 0.008 |

Модель эмбеддингов выбиралась так же, по одному фактору за раз: при 1000/200
`multilingual-MiniLM-L12` даёт hit@5 0.192 против 0.308 у англоязычной, которая
сейчас и стоит.

**Читать колонку `cov@5`, а не `hit@5`.** Потолок hit съезжает вместе с размером
чанка — 25, 24, 23, потом 12, — поэтому эти четыре числа лежат в разных
шкалах. Потолок покрытия равен 26 в каждой строке, потому что k подряд идущих
чанков восстанавливают непрерывного текста гораздо больше, чем нужно самой
длинной эталонной цитате. Именно `cov@5` сравнивает конфигурации, а не везение с
границами.

Что из этого следует:

- **800/160 выигрывает по всем колонкам** — прежнее решение выдержало
  перепроверку метрикой без потолка. И это единственная строка, где `cov@5`
  больше `hit@5`: одна запись отдана двумя кусками.
- **300/60 плох по-настоящему, а не из-за артефакта.** Снятие потолка учетверяет
  оценку (0.038 → 0.154), и она всё равно втрое хуже 800/160 — близко к
  множителю 3.9, который в [lessons.ru.md](lessons.ru.md) #6 был получен
  нормировкой, то есть совсем другим путём. А `coverage@5` 0.333 против `cov@5`
  0.154 объясняет, что мелкие чанки делают на самом деле: они дробят
  свидетельство, и ретривер приносит куски нужной цитаты, но редко всю её
  целиком.
