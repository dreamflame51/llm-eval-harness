llm-eval-harness · a RAG system and the instruments pointed at it

What checks what

A retrieval-augmented system answers questions about five NIST publications. The harness around it exists because retrieval that looks relevant is easy — so every stage below has an instrument pointed at it, and the interesting part is not the metrics but which of them a machine can run, and which need a model or a person.

This is the distinction the whole project is organised around. A number that can only be produced by a person is not worse than one CI prints — but it is a different kind of number, and pretending otherwise is how a harness ends up measuring only what is cheap.

What fails a build, and what does not

Six gates, four measurements, no thresholds

Gates — a test goes red

  • Every gold quote still appears in the corpus, verbatim.
  • Every reported number equals the value pinned in expected_metrics.json.
  • No single question changed verdict — the average can hold still while two records swap.
  • The judge's cache still describes the current prompt.
  • A hand label travels to a new recording only if the answer and every chunk are identical.
  • Every test and evidence path named in the traceability matrix exists.

Measurements — a number a person reads

  • Retrieval: hit@5, covered@5, coverage@5, MRR.
  • Refusal, judged, and the phrase-list tripwire beside it.
  • RAGAS against DeepEval on identical answers.
  • Agreement between the judges, and with the hand labels.

No acceptance threshold has been agreed for any metric in this project. The reason is on the page: this one moves in steps of one record out of twelve, so a bar on the average is either “one record” or nothing. What is gated instead is equality, and a verdict flipping.

Why any of it earns its keep

Four things the instruments caught that reading the code would not

the fixture
The frozen answers described a retriever we had replaced
BM25 was fused into retrieval; the answerable set was re-recorded and the labelled refusal set was not. For a day the reported refusal metric described the old system. Caught by the live check on its first real run — and both headline numbers were identical across the change, while three of twelve questions behaved differently.
the instrument
A cache keyed by the question, not by what was judged
Judging a second recording of the same twelve questions gave the older recording the newer verdicts. The cache key had always covered the answer and the chunks; the lookup threw that away. Caught by the per-question gate within minutes of being introduced.
the trade
Better retrieval, worse grounding — and only a human could see it
Fusing BM25 in raised hit@5 from 0.423 to 0.538 and cost two records of grounding. Every automated instrument reads all three recordings identically; the hand labels do not. Establishing it needed a control: the same twelve questions recorded the same afternoon through the old retriever.
the reason
The change worked; the explanation written next to it did not
BM25 went in because “the misses are questions naming a document, and exact strings are what word matching does better”. Neither of the two gold spans contains the identifier, and neither question is retrieved today. The improvement is real and lands on four other records. An intervention that moves the metric is not evidence for the reason you gave.
